% ABSTRACT
% ─────────────────────────────────────────────────────────────
\begin{abstract}
Aura is a hybrid secure-messaging research protocol that targets post-quantum confidentiality for session secrets under classical Ed25519 identity and signed-pre-key authentication. It uses X25519 and ML-KEM-768 in the initial X3DH-style handshake and again on directed ratchet steps. After a local endpoint-state compromise, classical recovery follows the first honest directed step; after a two-endpoint state compromise, recovery is tied to the next directed step that uses post-compromise peer DH and KEM material.

The construction binds each new KEM public key into the HKDF transcript and separates payload encryption from metadata encryption by using an independent per-epoch metadata key. Relative to Signal \SPQR{}/Triple Ratchet and Apple \PQThree{}, Aura does not claim priority for post-quantum ratcheting or deployment maturity. Its narrower contribution is a reproducible two-party design point: eager per-direction X25519+ML-KEM ratchet transitions, HKDF-info binding of the advertised KEM public key, a rotating envelope-metadata key, and claim-to-code links in one Rust artifact.

The security argument consists of six reduction-style theorems under Gap-CDH, ML-KEM IND-CCA2, dual-PRF, and MRAE assumptions. Symbolic evidence is deliberately scoped: 10 Tamarin lemmas verify a two-DH handshake abstraction and a terminal one-step ratchet abstraction, and 3 of 6 ProVerif queries discharge for the handshake/message-path model. The remaining ProVerif queries are not counted as machine-checked results. The Rust artifact implements the analyzed two-party protocol and includes deterministic vectors, reproducibility scripts, regression tests, and an implementation cross-reference map; implementation-wide line and test counts are artifact context, not separate security evidence.
\end{abstract}

\smallskip
\noindent\textbf{Keywords:} Post-quantum cryptography, secure messaging, double ratchet, hybrid key exchange, ML-KEM, formal verification, Tamarin, ProVerif.

\section{Introduction}\label{sec:intro}

Signal~\cite{signal-x3dh,cohn-gordon2020} is widely deployed in end-to-end encrypted messaging, including WhatsApp, Signal Messenger, and Google Messages. X3DH and the Double Ratchet provide forward secrecy and post-compromise security under elliptic-curve Diffie--Hellman assumptions.

The deployment pressure is broader than consumer chat. Operational systems increasingly combine mobile endpoints, UAV-assisted inspection, multimodal sensor streams, and SCADA-linked monitoring~\cite{svystun2025dytam,svystun2024thermal,lysyi2025fire}. In such settings, a messaging channel may carry coordination data, alerts, or inspection-derived evidence whose confidentiality must survive long device lifetimes and delayed adversarial analysis.

Cryptographically relevant quantum computers would break the classical assumptions behind this design. NIST has standardized ML-KEM as a lattice-based key-encapsulation mechanism~\cite{fips203}, but using a KEM inside a stateful messaging protocol is not a drop-in replacement for ECDH. Four protocol-design issues arise when a KEM is incorporated into a stateful ratchet:

\paragraph{Challenge 1: Harvest-now-decrypt-later attacks.}
An adversary that records ECDH-based traffic today could later derive affected session secrets if a CRQC becomes available. Forward secrecy based solely on ephemeral ECDH provides no protection against that setting, as Shor's algorithm~\cite{shor1997} efficiently solves the discrete logarithm problem on elliptic curves.

\paragraph{Challenge 2: KEM integration granularity.}
The Signal PQXDH proposal~\cite{signal-pqxdh} introduces a single Kyber encapsulation during the initial handshake but does not include post-quantum key material in subsequent ratchet steps. This protects the start of the session against harvest-now-decrypt-later attacks, but post-compromise recovery after the handshake relies on classical DH. More recent systems, including Signal \SPQR{}/Triple Ratchet~\cite{signal-spqr,signal-double-ratchet,mlkem-braid} and Apple \PQThree{}~\cite{apple-pq3,stebila-pq3,linker-pq3}, move post-quantum material into ongoing state evolution. Aura should therefore be compared with ongoing post-quantum ratcheting designs, not only with PQXDH.

\paragraph{Challenge 3: Directed KEM recovery in this construction.}
Unlike DH, a KEM schedule must advertise encapsulation material before the peer can encapsulate. In Aura's directed KEM-public-key schedule, a two-endpoint state compromise exposes the peer DH and KEM state used by the first post-compromise directed step. One-step classical recovery is therefore claimed only for local compromise, or for a model where the peer DH private scalar remains undisclosed. Under full two-endpoint state compromise, recovery is delayed until a directed step uses peer DH and KEM material generated after the compromise. Other SCKA-style schedules make different latency, bandwidth, and state-retention tradeoffs.

\paragraph{Challenge 4: Metadata leakage.}
Standard Double Ratchet implementations transmit ratchet public keys and message counters in cleartext envelope headers~\cite{signal-double-ratchet}. Even with payload encryption, such fields reveal ordering and lifecycle information. Aura encrypts a narrower inner envelope layer: message index, payload nonce, message type, and correlation identifiers. Delivery metadata, sizes, timing, and ratchet public material remain visible.

\medskip
\noindent\textbf{Contributions and novelty.} This paper does not claim
priority for the broad idea of post-quantum ratcheting; Signal
\SPQR{}/ML-KEM Braid~\cite{signal-spqr,signal-double-ratchet,mlkem-braid} and Apple
\PQThree{}~\cite{apple-pq3,stebila-pq3,linker-pq3} are the relevant modern baselines.
The contribution is a compact, open construction in which the protocol
mechanism, security claims, and Rust invariants can be audited together.
In particular, the paper makes five concrete contributions:

\begin{enumerate}
  \item \textbf{N1: per-direction hybrid ratcheting.} Every direction change triggers a full X25519~+~ML-KEM-768 key exchange and feeds both secrets into the next root key. The resulting PCS bound separates one-step classical recovery from two-step hybrid recovery (\cref{thm:pcs}).

  \item \textbf{N2: augmented HKDF key binding.} Each fresh ML-KEM public key is included in the HKDF info parameter during ratchet key derivation. A substituted key changes the derived root state and is detected at the next AEAD check; this does not replace identity authentication, but it binds the accepted KEM key without adding a per-ratchet signature (\cref{lem:augmented-hkdf}).

  \item \textbf{N3: two-layer AEAD with metadata-key rotation.} Envelope metadata and payload bytes are encrypted under separate keys. The metadata key rotates by epoch, and both layers use AES-256-GCM-SIV for nonce-misuse resistance (\cref{lem:two-layer}).

  \item \textbf{N4: explicit PCS asymmetry.} The analysis separates local endpoint compromise from conservative two-endpoint compromise. A local compromise admits one-step classical recovery; if the peer's current DH and KEM secrets are also exposed, recovery is delayed until a directed step uses post-compromise peer DH and KEM material.

  \item \textbf{N5: implementation cross-reference map.} The artifact records checkable links among the reduction-style theorems, supporting lemmas, scoped Tamarin/ProVerif models, Rust tests, benchmarks, and the protocol state machine.
\end{enumerate}

\section{Related Work}\label{sec:related}

\paragraph{Signal protocol.}
The Signal protocol, formalized by Cohn-Gordon et al.~\cite{cohn-gordon2020}, achieves forward secrecy and post-compromise security through the combination of X3DH key agreement~\cite{signal-x3dh} and the Double Ratchet algorithm. Its ratcheting behavior has received detailed symbolic and computational analysis~\cite{cohn-gordon2020,alwen2020,bienstock2020}. Its DH-derived session keys do not protect recorded traffic against a future adversary able to solve elliptic-curve discrete logarithms.

\paragraph{Post-quantum extensions to Signal.}
Signal's PQXDH protocol~\cite{signal-pqxdh} adds a single Kyber-1024 encapsulation to the X3DH handshake, providing initial quantum resistance. Brendel et al.~\cite{brendel2020} propose a generic post-quantum X3DH construction, and Hashimoto et al.~\cite{hashimoto2021} provide an efficient instantiation. These works are natural baselines for harvest-now-decrypt-later protection at session establishment, but not for post-quantum post-compromise recovery in a long-lived channel.

Signal \SPQR{}/Triple Ratchet~\cite{signal-spqr,signal-double-ratchet} is the relevant Signal-family comparison point for ongoing post-quantum state evolution. It runs a sparse post-quantum ratchet alongside the classical Double Ratchet and combines their message keys; its ML-KEM Braid component is specified as a Sparse Continuous Key Agreement protocol~\cite{mlkem-braid}. For a current comparison, PQXDH is therefore only the handshake baseline.

\paragraph{Industrial post-quantum messaging.}
Apple \PQThree{}~\cite{apple-pq3,stebila-pq3,linker-pq3} also moves post-quantum material beyond the initial handshake through periodic in-band rekeying, and has public reduction-style and Tamarin analyses. It is a deployed baseline, but its implementation is not open. This paper therefore does not claim priority for the broad idea of post-quantum ratcheting; it gives a compact Rust construction with explicit KEM-key binding, metadata-key rotation, and an artifact-level cross-reference between claims, tests, and implementation modules.

\paragraph{Ratcheting analysis.}
Alwen et al.~\cite{alwen2020} and Bienstock et al.~\cite{bienstock2020} give detailed analyses of Double Ratchet security notions, modularization, and post-compromise recovery. This line of work motivates the separation between the state-evolution claim and the concrete implementation invariants studied here.

\paragraph{Hybrid key exchange.}
The concept of hybrid key exchange---combining classical and post-quantum primitives---has been studied in the TLS context, including early CECPQ2 deployment experiments~\cite{cecpq2} and formal TLS~1.3 analyses~\cite{stebila2020,dowling2020}. These works establish security under the assumption that at least one component remains secure. The combiner in \cref{thm:hybrid-combiner} follows the same principle, using HKDF with the classical shared secret as salt and the KEM shared secret as input keying material.

\paragraph{Formal verification of messaging protocols.}
Tamarin~\cite{meier2013} and ProVerif~\cite{blanchet2016} have been used to verify properties of the Signal protocol~\cite{cohn-gordon2020}. The models in this paper adapt that line of analysis to a hybrid post-quantum setting, including custom equations for ML-KEM-768 and the Tamarin source-saturation issues caused by multiple DH operations.

\paragraph{Metadata privacy and anonymous delivery.}
Sealed Sender~\cite{sealed-sender} hides sender identity from Signal's service, while mix-network designs such as Sphinx~\cite{sphinx} and Loopix~\cite{loopix} address network-level anonymity. Aura's metadata layer is narrower: it encrypts protocol envelope fields under rotating per-epoch keys, complementing rather than replacing sender-hiding delivery systems.

\paragraph{Nonce-misuse-resistant AEAD.}
AES-256-GCM-SIV~\cite{rfc8452} provides misuse-resistant authenticated encryption, degrading to deterministic authenticated encryption under nonce reuse, whereas AES-GCM loses its standard confidentiality and integrity bounds under repeated nonces. Rogaway and Shrimpton~\cite{rogaway2006} formalize the MRAE security notion. We employ GCM-SIV as defense-in-depth alongside monotonic nonce counters.

\subsection{Cryptographic Primitives}

\begin{definition}[Diffie--Hellman on X25519]\label{def:dh}
The proof uses an idealized prime-order X25519 abstraction of order
$q = 2^{252} + 27742317777372353535851937790883648493$. Curve25519 has
cofactor 8; the implementation follows RFC~7748 clamping and rejects malformed
field encodings, small-order inputs, and all-zero shared secrets where
applicable. Cofactor and twist subtleties are not modeled beyond this
abstraction. The X25519 function~\cite{rfc7748} computes scalar multiplication
$\DH(a, B) = [a]B$ with base point $u = 9$.
\end{definition}

\begin{definition}[Gap-CDH]\label{def:gap-cdh}
The $\GapCDH$ assumption states that for all $\ppt$ adversaries $\advA$ with access to a DDH oracle $\oracle_{\mathrm{DDH}}$:
\begin{equation}\label{eq:gap-cdh}
  \adv^{\GapCDH}_G(\advA) = \Pr\!\left[\advA^{\oracle_{\mathrm{DDH}}}(G, [a]G, [b]G) = [ab]G \;\middle|\; a, b \getsr \mathbb{Z}_q\right] \leq \negl(\secpar).
\end{equation}
\end{definition}

\begin{definition}[Key Encapsulation Mechanism]\label{def:kem}
A KEM $\Pi = (\KeyGen, \Encaps, \Decaps)$ consists of key generation outputting $(pk, sk)$, encapsulation $\Encaps(pk) \to (ct, ss)$, and decapsulation $\Decaps(sk, ct) \to ss$, satisfying correctness: $\Decaps(sk, ct) = ss$ for $(ct, ss) \gets \Encaps(pk)$.
\end{definition}

\begin{definition}[IND-CCA2 for KEM]\label{def:ind-cca2}
The $\INDCCA$ advantage of $\advA$ against KEM $\Pi$ is:
\begin{equation}\label{eq:kem-ind-cca}
  \adv^{\INDCCA}_\Pi(\advA) = \left|\Pr\!\left[\advA^{\oracle_{\Decaps}}(pk, ct^*, ss_b) = b\right] - \frac{1}{2}\right| \leq \negl(\secpar),
\end{equation}
where $b \getsr \{0,1\}$, $(ct^*, ss_0) \gets \Encaps(pk)$, $ss_1 \getsr \{0,1\}^{256}$, and $\advA$ may not query $\oracle_{\Decaps}$ on $ct^*$.
\end{definition}

\begin{definition}[HKDF Dual-PRF Property~\cite{krawczyk2010}]\label{def:dual-prf}
$\HKDF$-$\SHA$ satisfies the $\dualPRF$ property if:
\begin{enumerate}
  \item \textbf{PRF in key (salt):} For a uniformly random salt $s$, $\HKDF(s, \cdot)$ is computationally indistinguishable from a random function.
  \item \textbf{PRF in input (IKM):} For a uniformly random IKM $k$, $\HKDF(\cdot, k)$ is computationally indistinguishable from a random function.
\end{enumerate}
\end{definition}

\begin{definition}[MRAE Security~\cite{rfc8452,rogaway2006}]\label{def:mrae}
$\AEAD$ satisfies $\MRAE$ security if:
\begin{itemize}
  \item Under unique nonces: full $\INDCPA$ + $\INTCTXT$ (standard AEAD security).
  \item Under nonce reuse: degrades to deterministic authenticated encryption (DAE), leaking equality patterns for repeated $(\mathit{nonce}, \mathit{AAD}, \mathit{plaintext})$ tuples while preserving $\INTCTXT$.
\end{itemize}
\end{definition}

\section{Protocol Design}\label{sec:protocol}

Aura consists of two phases: a \emph{hybrid X3DH handshake} (\cref{sec:handshake}) that establishes initial shared state, and a \emph{hybrid Double Ratchet} (\cref{sec:ratchet}) that continuously refreshes key material. Messages are protected by a \emph{two-layer AEAD} construction (\cref{sec:two-layer}).

\subsection{Pre-Key Bundle}\label{sec:bundle}

Each party $R$ publishes a pre-key bundle:
\begin{equation}\label{eq:prekey-bundle}
  \mathit{Bundle}_R = \bigl(v,\; ed_R^{\mathit{pub}},\; \IK_R^{\mathit{pub}},\;
  \mathit{spk\_id},\; \SPK_R^{\mathit{pub}},\;
  \sigma_{\SPK},\; \{(\mathit{opk\_id}_j,\OPK_{R,j}^{\mathit{pub}})\}_j,\;
  kpk_R,\; \sigma_{\mathit{IKX}}\bigr),
\end{equation}
where $\sigma_{\mathit{IKX}}=\textsf{Ed25519.Sign}(ed_R^{\mathit{sk}},\IK_R^{\mathit{pub}})$ binds the X25519 identity key to the Ed25519 identity key, $\sigma_{\SPK}=\textsf{Ed25519.Sign}(ed_R^{\mathit{sk}},\SPK_R^{\mathit{pub}})$ signs the medium-term pre-key, $\{\OPK_{R,j}\}$ is a set of one-time pre-keys, and $kpk_R$ is the ML-KEM public key. The KEM public key is validated and transcript-bound by key confirmation; it is not a separate Ed25519-signed object in the current artifact.

\subsection{Hybrid X3DH Key Agreement}\label{sec:handshake}

The handshake extends Signal's X3DH with an ML-KEM-768 encapsulation and bilateral key confirmation.

\begin{algorithm}[H]
\caption{Initiator X3DH computation.}\label{alg:initiator}
\DontPrintSemicolon
\KwIn{Initiator identity $(\IK_I, \EK_I)$; responder bundle $\mathit{Bundle}_R$}
\KwOut{Root key $\rk_0$, session state, init message}

Validate $\mathit{Bundle}_R$: verify $\sigma_{\SPK}$, reject small-order points, validate $kpk_R$\;
Generate ephemeral keypair $(\mathit{ek}_I, \EK_I^{\mathit{pub}})$\;
Select one-time pre-key $\OPK_R$ (if available)\;
\BlankLine
\Comment{Four X25519 DH computations}
$\mathit{dh}_1 \gets \DH(\mathit{ik}_I, \SPK_R^{\mathit{pub}})$\;
$\mathit{dh}_2 \gets \DH(\mathit{ek}_I, \IK_R^{\mathit{pub}})$\;
$\mathit{dh}_3 \gets \DH(\mathit{ek}_I, \SPK_R^{\mathit{pub}})$\;
$\mathit{dh}_4 \gets \DH(\mathit{ek}_I, \OPK_R^{\mathit{pub}})$ \hfill\Comment{if OPK present}
\BlankLine
\Comment{Classical shared secret}
$\mathit{IKM} \gets \mathtt{0xFF}^{32} \concat \mathit{dh}_1 \concat \mathit{dh}_2 \concat \mathit{dh}_3 [\concat \mathit{dh}_4]$\;
$\mathit{cs} \gets \HKDF(\mathit{IKM},\, 32,\, \varepsilon,\, \texttt{"Aura-X3DH"})$\;
\BlankLine
\Comment{ML-KEM-768 encapsulation}
$(\mathit{ct}_{\mathit{ky}},\, \mathit{ss}_{\mathit{ky}}) \gets \KEM.\Encaps(kpk_R)$\;
\BlankLine
\Comment{Hybrid combiner (classical as salt, PQ as IKM)}
$\rk_0 \gets \HKDF(\mathit{ss}_{\mathit{ky}},\, 32,\, \mathit{cs},\, \texttt{"Aura-Hybrid-X3DH"})$\;
\BlankLine
\Comment{Derive session keys}
$\mathit{sid} \gets \HKDF(\rk_0,\, 16,\, \mathit{ct}_{\mathit{ky}},\, \texttt{"Aura-SessionId"})$\;
$\mathit{ctx}_{\mathit{md}} \gets \mathrm{sort}(\EK_I^{\mathit{pub}}, \SPK_R^{\mathit{pub}}) \concat \mathit{sid}$\;
$\mdk_0 \gets \HKDF(\rk_0,\, 32,\, \mathit{ctx}_{\mathit{md}},\, \texttt{"Aura-MetadataKey"})$\;
$\mathit{kc}_I \gets \HKDF(\rk_0,\, 32,\, \varepsilon,\, \texttt{"Aura-KeyConfirm-I"})$\;
$\mathit{kc}_R \gets \HKDF(\rk_0,\, 32,\, \varepsilon,\, \texttt{"Aura-KeyConfirm-R"})$\;
\BlankLine
\Comment{Key confirmation}
$m_I^{\mathit{bind}} \gets \texttt{"Aura-Handshake-Init-Identity-Binding"} \concat \mathit{ed}_I^{\mathit{pub}} \concat \IK_I^{\mathit{pub}} \concat kpk_I$\;
$\sigma_I^{\mathit{bind}} \gets \textsf{Ed25519.Sign}(ik_I^{\mathit{ed}},\, m_I^{\mathit{bind}})$\;
$\mathit{Init}_0 \gets \mathit{Init}\text{ with } \mathit{mac}_I = 0$\;
$\mathit{th} \gets \HMAC(\texttt{"Aura-Handshake-Transcript"},\, \mathsf{LP}(\mathit{Bundle}_R) \concat \mathsf{LP}(\mathit{Init}_0))$\;
$\mathit{mac}_I \gets \HMAC(\mathit{kc}_I,\, \mathit{th})$\;
\BlankLine
Send $\mathit{Init} = (\mathit{ed}_I^{\mathit{pub}},\, \IK_I^{\mathit{pub}},\, \EK_I^{\mathit{pub}},\, \mathit{ct}_{\mathit{ky}},\, kpk_I,\, \sigma_I^{\mathit{bind}},\, \mathit{mac}_I,\, \mathit{opk\_id},\, N_{\max})$\;
Store $\mathit{mac}_R^* \gets \HMAC(\mathit{kc}_R,\, \mathit{th})$ for verification\;
Erase $\mathit{ek}_I$, copies of $\mathit{ik}_I$, all $\mathit{dh}_i$, $\mathit{cs}$, $\mathit{ss}_{\mathit{ky}}$\;
\end{algorithm}

Here $\mathsf{LP}(x)$ denotes the length-prefixed canonical encoding used by the transcript serializer.

The responder performs the symmetric computation: it recomputes the four DH shared secrets using its own private keys, decapsulates the ML-KEM ciphertext, derives the same root key $\rk_0$, verifies $\mathit{mac}_I$, and sends $\mathit{Ack} = (\mathit{mac}_R)$. The initiator finalizes by verifying $\mathit{mac}_R$ in constant time.

\paragraph{Hybrid combiner design.}
The combiner uses the classical DH output $\mathit{cs}$ as the HKDF salt and the ML-KEM shared secret $\mathit{ss}_{\mathit{ky}}$ as input keying material. This matches the RFC~5869 extract-and-expand interface~\cite{rfc5869} and relies on the $\dualPRF$ property of HKDF: the output $\rk_0$ is pseudorandom provided either the salt (classical) or the IKM (post-quantum) is uniformly random. Concretely, if the classical DH assumption holds, $\mathit{cs}$ is computationally indistinguishable from random (as a salt), and if ML-KEM-768 is $\INDCCA$ secure, $\mathit{ss}_{\mathit{ky}}$ is indistinguishable from random (as IKM). The hybrid combiner remains secure as long as at least one assumption holds.

\paragraph{Key confirmation.}
Bilateral key confirmation prevents unknown key-share (UKS) attacks~\cite{lamacchia2007}. The transcript digest $\mathit{th}$ is computed with HMAC's prefix-safe encoding structure over length-prefixed inputs; the authentication step is the later HMAC under keys $\mathit{kc}_I$ and $\mathit{kc}_R$. These confirmation keys are derived from $\rk_0$ using distinct HKDF info strings, ensuring domain separation.

\paragraph{DH validation.}
All received X25519 public keys are validated by checking against the eight small-order points of Curve25519 (points of order dividing the cofactor 8) using constant-time comparison to prevent timing side-channels. Additionally, points are verified to satisfy $\mathit{key} < p$ where $p = 2^{255} - 19$, using branchless word-by-word subtraction.

\subsection{Hybrid Double Ratchet}\label{sec:ratchet}

After the handshake, communication proceeds via the hybrid Double Ratchet, which combines a symmetric-key chain ratchet with an asymmetric hybrid ratchet.

\subsubsection{Symmetric Chain Ratchet}

Message keys are derived from the chain key via HKDF with distinct info strings for domain separation:
\begin{align}
  \mk_{e,n} &= \HKDF(\ck_e^{(n)},\, 32,\, \varepsilon,\, \texttt{"Aura-Msg"}), \label{eq:msg-key} \\
  \ck_e^{(n+1)} &= \HKDF(\ck_e^{(n)},\, 32,\, \varepsilon,\, \texttt{"Aura-Chain"}). \label{eq:chain-key}
\end{align}
The old chain key $\ck_e^{(n)}$ is securely erased after derivation, providing per-message forward secrecy within an epoch.

\subsubsection{Asymmetric Hybrid Ratchet}

\begin{algorithm}[H]
\caption{Send-side hybrid ratchet (epoch $e \to e+1$).}\label{alg:send-ratchet}
\DontPrintSemicolon
\KwIn{Current root key $\rk_e$, peer's DH public key $D_{\mathit{peer}}$, peer's ML-KEM public key $kpk_{\mathit{peer}}$}
\KwOut{New root key $\rk_{e+1}$, new chain key $\ck_{e+1}$, new metadata key $\mdk_{e+1}^{\mathit{send}}$, ratchet header}

Generate fresh X25519 keypair $(d_{e+1}, D_{e+1})$\;
$\mathit{dh}_{e+1} \gets \DH(d_{e+1}, D_{\mathit{peer}})$\;
$(\mathit{ct}_{e+1}, \mathit{ss}_{e+1}) \gets \KEM.\Encaps(kpk_{\mathit{peer}})$\;
Generate fresh ML-KEM keypair $(kpk_{e+1}, ksk_{e+1})$\;
\BlankLine
$\mathit{ikm} \gets \mathit{dh}_{e+1} \concat \mathit{ss}_{e+1}$\;
$\mathit{info} \gets \texttt{"Aura-Hybrid-Ratchet"} \concat kpk_{e+1}$\;
$(\rk_{e+1} \concat \ck_{e+1} \concat \mdk_{e+1}^{\mathit{send}}) \gets \HKDF(\mathit{ikm},\, 96,\, \rk_e,\, \mathit{info})$\;
\BlankLine
Attach $(D_{e+1},\, \mathit{ct}_{e+1},\, kpk_{e+1})$ to envelope header\;
Erase $d_e$, $ksk_e$, $\rk_e$, $\mathit{dh}_{e+1}$, $\mathit{ss}_{e+1}$\;
\end{algorithm}

\paragraph{Ratchet trigger.}
In the classical Double Ratchet, the DH ratchet advances when a new DH public key is received from the peer~\cite{signal-double-ratchet}; Signal's current Triple Ratchet adds \SPQR{} as a separate sparse post-quantum component~\cite{signal-spqr,mlkem-braid}. Aura instead uses one protocol-level policy for this design point: after every received message, the \texttt{send\_ratchet\_pending} flag causes the next \texttt{encrypt()} call to execute a full hybrid ratchet. Additionally, a chain exhaustion ratchet is triggered when the negotiated per-chain limit is reached; the public API default is 1{,}000 messages and the protocol cap is 10{,}000.

\paragraph{Augmented info string.}
The HKDF info parameter includes the new ML-KEM public key $kpk_{e+1}$ (\cref{alg:send-ratchet}, line~7). This binding supports the following lemma:

\begin{lemma}[Augmented HKDF Info Binding]\label{lem:augmented-hkdf}
If an adversary substitutes $kpk' \neq kpk_{e+1}$ in the ratchet header, the receiver computes a different root key $\rk'_{e+1} \neq \rk_{e+1}$ with overwhelming probability (under the $\PRF$ property of HKDF). Consequently, all derived chain and message keys differ, and AEAD decryption fails (under the $\INTCTXT$ property of $\AEAD$). This provides an implicit state-binding check for the KEM public key without per-step signatures; it is not a separate identity-authentication mechanism.
\end{lemma}

\paragraph{Receive-side ratchet.}
The receiver mirrors the computation: it decapsulates the KEM ciphertext, computes the DH shared secret, derives the new root key using the augmented info string, and caches the old metadata key for decrypting delayed messages from previous epochs.

\paragraph{Transactional rollback.}
Before applying a received ratchet, the implementation snapshots the full session state (root key, chain keys, DH/ML-KEM private keys, skipped key cache, metadata key cache). If metadata or payload decryption fails after the ratchet is applied, the snapshot is restored, preventing a forged ratchet envelope from desynchronizing the peers.

\subsubsection{Session Initialization}

After the X3DH handshake produces $\rk_0$ and the ML-KEM shared secret, the session is initialized via an initial hybrid ratchet step:
\begin{align}
  \mathit{dh}_{\mathit{init}} &= \DH(d_{\mathit{local}}, D_{\mathit{remote}}), \label{eq:init-dh} \\
  \mathit{hybrid\_ikm} &= \mathit{dh}_{\mathit{init}} \concat \mathit{ss}_{\mathit{ky}}, \label{eq:init-hybrid-ikm} \\
  T_{\mathit{init}} &= \HKDF(\mathit{hybrid\_ikm},\, 64,\, \rk_0,\, \texttt{"Aura-Hybrid-Ratchet"}), \label{eq:init-transcript} \\
  \rk_1 &= T_{\mathit{init}}[0{:}32], \label{eq:init-root-key} \\
  (\ck_{\mathit{send}},\, \ck_{\mathit{recv}}) &= \HKDF(\rk_1,\, 64,\, \varepsilon,\, \texttt{"Aura-ChainInit"}). \label{eq:init-chain-keys}
\end{align}
The final post-handshake root used by the message layer is $\rk_1$; $\mdk_0$ remains the initial metadata key until the first ratchet. The initiator uses the first 32 bytes of \texttt{Aura-ChainInit} output as $\ck_{\mathit{send}}$ and the last 32 bytes as $\ck_{\mathit{recv}}$; the responder swaps them. The AKE theorem establishes pseudorandomness of $\rk_0$; the post-handshake initialization carries this to $(\rk_1,\ck_{\mathit{send}},\ck_{\mathit{recv}})$ by HKDF domain separation with $\rk_0$ as salt.

\subsection{Two-Layer AEAD Encryption}\label{sec:two-layer}

Each message envelope consists of two independently encrypted layers:

\paragraph{Layer 1: Metadata.}
\begin{equation}\label{eq:metadata-aead}
  \mathit{ct}_{\mathit{md}} = \AEAD.\Enc(\mdk_e^{\mathit{send}},\, \mathit{nonce}_{\mathit{md}},\, \mathit{metadata},\, \mathit{aad}_{\mathit{md}}),
\end{equation}
where $\mathit{aad}_{\mathit{md}} = \mathit{sid} \concat \mathit{ibh} \concat \epoch \concat v$ includes the session ID, identity binding hash, epoch counter, and protocol version. The metadata contains the message index, payload nonce, envelope type, and correlation identifiers.

\paragraph{Layer 2: Payload.}
\begin{equation}\label{eq:payload-aead}
  \mathit{ct}_{\mathit{pay}} = \AEAD.\Enc(\mk_{e,n},\, \mathit{nonce}_{\mathit{pay}},\, \mathit{plaintext},\, \mathit{aad}_{\mathit{pay}}),
\end{equation}
where $\mathit{aad}_{\mathit{pay}} = \mathit{sid} \concat \mathit{ibh} \concat \epoch \concat n \concat v$ additionally includes the message index $n$.

\begin{lemma}[Two-Layer AEAD Independence]\label{lem:two-layer}
For a ratchet epoch, the chain key $\ck_e$ and metadata key $\mdk_e$ are disjoint segments of a jointly pseudorandom HKDF output; the payload message key $\mk_{e,n}$ is later derived from $\ck_e$ under the \texttt{"Aura-Msg"} domain label. Given only $\mk_{e,n}$ and not the root or metadata key material, the adversary obtains no information about $\mdk_e$ under the HKDF PRF assumption and the one-way chain derivation.
\end{lemma}

\paragraph{Nonce structure.}
Payload nonces use a structured 12-byte layout:
\begin{equation}\label{eq:nonce-layout}
  \mathit{nonce} =
  \mathit{prefix}[8] \concat
  \mathit{counter}_{\mathrm{LE}}[2] \concat
  \mathit{msg\_index}_{\mathrm{LE}}[2].
\end{equation}
The prefix is sampled by the CSPRNG when the send nonce generator is created
or reset at a ratchet boundary, the counter is monotonically increasing,
and the message index provides per-chain addressability. Metadata encryption
uses an independent random 12-byte \texttt{header\_nonce}. The implementation
forces a ratchet at the negotiated message-chain limit (default 1{,}000, cap 10{,}000), before
either 16-bit field is exhausted, and emits a nonce-budget warning when the
remaining budget falls to 10\% or below.

\paragraph{Identity binding hash.}
Every AEAD additional-data construction includes an identity binding hash:
\begin{equation}\label{eq:identity-binding}
  \mathit{ibh} = \SHA(\texttt{"Aura-Identity-Binding"} \concat \mathrm{sort}(\mathit{ed}_I, \mathit{ed}_R) \concat \mathrm{sort}(\mathit{x}_I, \mathit{x}_R)),
\end{equation}
where both Ed25519 and X25519 public key pairs are lexicographically sorted before concatenation. This binds AEAD data to the unordered pair of identities. Role separation is provided by the handshake transcript, key-confirmation direction labels, and initiator/responder chain-key assignment.

\subsection{Replay Protection}\label{sec:replay}

Replay protection is achieved through a bounded nonce cache:
\begin{itemize}
  \item A $\mathsf{HashSet}$ of seen payload nonces, bounded to $W = 2{,}048$ entries.
  \item Nonces embed a monotonic counter (bytes $[8{:}10]$); when the cache is full, the oldest observed nonce entries are evicted first.
  \item Duplicate nonces are immediately rejected before payload decryption.
\end{itemize}

\subsection{State Persistence}\label{sec:state}

Session state is serialized via Protocol Buffers and protected by two mechanisms:
\begin{itemize}
  \item \textbf{State integrity HMAC:} An HMAC-SHA256 tag computed over the serialized state (key derived from the root key via $\HKDF$) authenticates serialized-state integrity. Rollback freshness requires the external monotonic counter used by sealed-state import/export.
  \item \textbf{Sealed export:} For persistent storage, the state is encrypted using a double-envelope construction: a random data encryption key (DEK) encrypts the state, and the DEK is encrypted under a caller-provided key encryption key (KEK), both using $\AEAD$.
\end{itemize}

\section{Security Model}\label{sec:security-model}

We use an $\eCK$-style AKE model~\cite{canetti2001,lamacchia2007} adapted to the hybrid post-quantum setting. The oracle set is stated explicitly below; claims should be read against this leakage model rather than as a blanket proof for every eCK variant in the literature.

\begin{definition}[Parties and Sessions]\label{def:parties}
There are at most $N$ parties, each holding an X25519 identity keypair $\IK_i$, an Ed25519 signing keypair, an ML-KEM-768 keypair $(kpk_i, ksk_i)$, rotating signed pre-keys, and one-time pre-keys. A session $\pi_i^s$ denotes a protocol run by party $P_i$ with intended partner $P_j$.
\end{definition}

\begin{definition}[Adversary Oracles]\label{def:oracles}
The adversary $\advA$ has access to the following oracles:
\begin{itemize}
  \item $\textsf{Send}(\pi_i^s, m)$: Deliver message $m$ to session $\pi_i^s$ and obtain the response.
  \item $\textsf{Corrupt}(P_i)$: Obtain all long-term keys of $P_i$ ($\mathit{ik}_i$, Ed25519 signing key, $ksk_i$).
  \item $\textsf{RevealSPK}(P_i,\mathit{spk\_id})$: Obtain the private scalar for a selected signed pre-key.
  \item $\textsf{RevealOPK}(P_i,\mathit{opk\_id})$: Obtain the private scalar for an unused one-time pre-key. Consumed OPKs are modeled as deleted.
  \item $\textsf{RevealState}(\pi_i^s)$: Obtain the full session state (root key, chain keys, metadata keys, DH/ML-KEM private keys, nonce state).
  \item $\textsf{RevealSessionKey}(\pi_i^s)$: Obtain the current root key $\rk_e$.
  \item $\textsf{Test}(\pi_i^s)$: Challenge oracle. Flip coin $b \getsr \{0,1\}$; return $\rk_e$ if $b = 0$, or a uniformly random key if $b = 1$. At most one $\textsf{Test}$ query is allowed.
\end{itemize}
\end{definition}

\begin{definition}[Partnering]
Sessions $\pi_i^s$ and $\pi_j^t$ are \emph{partnered} if they share the same transcript hash $\mathit{th}$.
\end{definition}

\begin{definition}[Freshness]\label{def:freshness}
A session $\pi_i^s$ with partner $\pi_j^t$ is \emph{fresh} if the adversary has not:
\begin{enumerate}
  \item Queried $\textsf{RevealSessionKey}$ or $\textsf{RevealState}$ on either $\pi_i^s$ or $\pi_j^t$ before $\textsf{Test}$.
  \item Queried both $\textsf{Corrupt}(P_i)$ and $\textsf{RevealState}(\pi_i^s)$ before the tested session completed.
  \item Queried $\textsf{Corrupt}(P_j)$ before session $\pi_j^t$ was created and no OPK was used.
  \item Queried $\textsf{RevealSPK}(P_j,\mathit{spk\_id})$ for the responder signed pre-key used in the tested session before $\textsf{Test}$ and no OPK was used and deleted.
  \item Queried $\textsf{RevealOPK}(P_j,\mathit{opk\_id})$ for the OPK used in the tested session before it was consumed.
\end{enumerate}
\end{definition}

\begin{definition}[$\eCK$-Style AKE Security]\label{def:ake}
The Aura protocol is secure in the model above if for all $\ppt$ adversaries $\advA$:
\begin{equation}\label{eq:eck-advantage}
  \adv^{\eCK}_{\mathrm{AURA}}(\advA) = \left|\Pr[\advA \text{ wins}] - \frac{1}{2}\right| \leq \negl(\secpar),
\end{equation}
where $\advA$ wins by correctly guessing $b$ for a fresh tested session.
\end{definition}

\begin{definition}[Forward Secrecy]\label{def:fs}
Compromise of long-term identity and KEM keys $(\IK_I, \IK_R, ksk_I, ksk_R)$ at time $t$ does not allow decryption of messages encrypted before $t$ in sessions whose key agreement completed before the compromise, provided the responder signed-pre-key private scalar remains undisclosed or a consumed OPK private scalar was used and deleted.
\end{definition}

\begin{definition}[Post-Compromise Security~\cite{cohn-gordon2020}]\label{def:pcs}
After full state compromise at epoch $e$ via $\textsf{RevealState}$, messages at epoch $\geq e + k$ are secure, provided the adversary does not compromise new keys generated after epoch $e$. We distinguish $k = 1$ (classical PCS) and $k = 2$ (hybrid PCS).
\end{definition}

\section{Security Analysis}\label{sec:proofs}

This section states six security theorems for the Aura protocol. The paper keeps the theorem statements and proof sketches in line with the main construction and the accompanying formal models.

\subsection{Theorem 1: Hybrid Root-Key Pseudorandomness}\label{sec:thm1}

\begin{theorem}[Hybrid Root-Key Pseudorandomness]\label{thm:hybrid-combiner}
If $\KEM$ is $\INDCCA$ secure \textbf{or} $\DH$ satisfies $\GapCDH$ in the $\ROM$, then the Aura hybrid combiner
\begin{equation}\label{eq:combiner-root}
  \rk_0 = \HKDF(\mathit{ss}_{\mathit{ky}},\, 32,\, \mathit{cs},\, \texttt{"Aura-Hybrid-X3DH"})
\end{equation}
outputs a pseudorandom root key. Concretely:
\begin{equation}\label{eq:combiner-bound}
  \adv^{\mathsf{rk}}_{\mathrm{Hybrid}}(\advA)
  \leq
  \min\!\left\{
    \adv^{\INDCCA}_{\KEM}(\advB_1),
    4 \cdot \adv^{\GapCDH}_{\DH}(\advB_2)
  \right\}
  + \adv^{\dualPRF}_{\HKDF}(\advB_3) + \frac{q_H}{2^{256}},
\end{equation}
where $q_H$ is the number of random oracle queries and the factor 4 arises from the four DH key pairs in the classical X3DH component.
\end{theorem}

\begin{proof}[Proof sketch]
There are two reduction paths. In the KEM path, we replace the ML-KEM shared
secret $\mathit{ss}_{\mathit{ky}}$ with a uniformly random value, reducing
the distinguishing advantage to $\adv^{\INDCCA}_{\KEM}(\advB_1)$. In the
classical path, we replace the X3DH shared secret $\mathit{cs}$ with a random
value via the $\GapCDH$ oracle; the factor~4 accounts for guessing one of the
four DH pairs $\mathit{dh}_1, \ldots, \mathit{dh}_4$. Either path leaves at
least one HKDF input (IKM or salt) uniformly random, so the $\dualPRF$
property makes $\rk_0$ indistinguishable from random. Taking the tighter of
the two paths yields \cref{eq:combiner-bound}; the $q_H/2^{256}$ term bounds
random oracle collisions.
\end{proof}

\subsection{Theorem 2: AKE Security}

\begin{theorem}[AKE Security in the Modified X3DH Leakage Model]\label{thm:ake}
The Aura hybrid X3DH satisfies the AKE security definition above. For any $\ppt$ adversary $\advA$ making at most $q_s$ session queries:
\begin{align}
  \adv^{\eCK}_{\mathrm{AURA}}(\advA)
  &\leq q_s \cdot \big(
    4 \cdot \adv^{\GapCDH}_{\DH}(\advB_1)
    + \adv^{\INDCCA}_{\KEM}(\advB_2) \\
  &\qquad
    + \adv^{\dualPRF}_{\HKDF}(\advB_3)
    + 2 \cdot \adv^{\PRF}_{\HMAC}(\advB_4)\big)
    + \frac{q_s^2}{2^{128}} + \frac{q_H}{2^{256}}. \label{eq:ake-bound}
\end{align}
\end{theorem}

\begin{proof}[Proof sketch]
The reduction uses five standard hybrid transitions. First, the reduction guesses the tested session, losing a factor $q_s$. Next, it replaces the DH outputs, KEM shared secret, and HKDF output with random values, as in \cref{thm:hybrid-combiner}. Finally, it replaces the key confirmation MACs with random tags, reducing to $\PRF$ security of $\HMAC$; the factor~2 accounts for $\mathit{mac}_I$ and $\mathit{mac}_R$. The term $q_s^2/2^{128}$ bounds 128-bit session ID collisions.
\end{proof}

\begin{lemma}[Bilateral Key Confirmation Prevents UKS]\label{lem:key-confirm}
An adversary who does not know $\rk_0$ cannot forge a valid key confirmation MAC, since $\mathit{kc}_I$ and $\mathit{kc}_R$ are derived from $\rk_0$ via HKDF with distinct info strings, and the MAC is computed over the full transcript hash binding both parties' identities and ephemeral keys.
\end{lemma}

\begin{lemma}[Domain Separation]\label{lem:domain-sep}
The implementation defines domain labels in the constants module. HKDF domain separation applies only to labels used as HKDF \texttt{info} values. The handshake-transcript, identity-binding, init-identity-binding, and PQ-hybrid labels are domain separators for HMAC, hashing, signatures, or helper paths rather than HKDF labels. For HKDF calls, distinct \texttt{info} values correspond to distinct oracle inputs in the $\ROM$ and to distinct PRF inputs in the standard model.
\end{lemma}

\subsection{Theorem 3: Forward Secrecy}

\begin{theorem}[Forward Secrecy]\label{thm:fs}
For any $\ppt$ adversary $\advA$ who obtains the long-term identity and KEM keys at time $t$, and for sessions whose responder signed-pre-key private scalar remains undisclosed or whose consumed OPK private scalar has already been deleted:
\begin{equation}\label{eq:fs-bound}
  \adv^{\mathrm{FS}}_{\mathrm{AURA}}(\advA) \leq \adv^{\GapCDH}_{\DH}(\advB_1) + \adv^{\dualPRF}_{\HKDF}(\advB_2).
\end{equation}
This is a classical forward-secrecy bound under later disclosure of long-term
KEM secret keys. If both the responder SPK private scalar and KEM secret key
are later disclosed, and no deleted OPK contributed to the transcript, this
classical FS theorem does not apply. The initial KEM ciphertext gives
harvest-now-decrypt-later protection only while the corresponding KEM secret
key is not later disclosed.
\end{theorem}

\begin{proof}[Proof sketch]
In the first hybrid transition, security comes from a DH term whose private scalar is unavailable
after compromise: $\mathit{dh}_3$ if the responder SPK private scalar is not
revealed, or $\mathit{dh}_4$ if a consumed OPK was used and deleted. The
transcript-visible term $\mathit{dh}_2=\DH(\mathit{ek}_I,\IK_R^{\mathit{pub}})$
is not counted after $\mathit{ik}_R$ disclosure, because it can be recomputed
from $\IK_R$ and $\EK_I^{\mathit{pub}}$. The surviving classical shared secret
is used as the HKDF salt, so the $\dualPRF$ property makes the root key
pseudorandom. The initial KEM term is intentionally not counted in this FS bound:
after later disclosure of $\mathit{ksk}_R$, a recorded KEM ciphertext can be
decapsulated. The KEM contribution in this setting is HNDL protection without
later KEM secret-key disclosure, and PCS after fresh ratchet KEM keys appear.
\end{proof}

\begin{lemma}[Ephemeral Key Erasure]\label{lem:erasure}
The implementation erases temporary copies and intermediate DH outputs immediately after use via \texttt{zeroize} (volatile writes with compiler barriers). The X25519 key that becomes the current ratchet private state is retained in guarded session memory until the next ratchet replaces it; it is not counted as erased while it remains active state.
\end{lemma}

\subsection{Theorem 4: Post-Compromise Security}\label{sec:thm-pcs}

\begin{theorem}[Post-Compromise Security]\label{thm:pcs}
If the adversary compromises session state at epoch $e$ via
$\textsf{RevealState}$ and then stops learning post-compromise secrets:

\noindent\textbf{(a) Local classical PCS (1-step):} If the compromise is local to the sender endpoint, or more generally the peer DH private scalar used by the next directed DH remains undisclosed, messages after the first honest directed ratchet step are secure:
\begin{equation}\label{eq:pcs-classical-bound}
  \adv^{\mathrm{PCS}\text{-}1}_{\mathrm{AURA}}(\advA) \leq \adv^{\GapCDH}_{\DH}(\advB_1) + \adv^{\dualPRF}_{\HKDF}(\advB_2).
\end{equation}

\noindent\textbf{(b) Two-endpoint hybrid recovery:} If both endpoints' epoch-$e$ DH and KEM ratchet secrets are exposed, no first-step PCS is claimed. Messages after the next directed step that uses post-compromise peer DH and KEM public keys are secure:
\begin{equation}\label{eq:pcs-hybrid-bound}
  \adv^{\mathrm{PCS}\text{-}2}_{\mathrm{AURA}}(\advA) \leq \adv^{\GapCDH}_{\DH}(\advB_1) + \adv^{\INDCCA}_{\KEM}(\advB_3) + 2 \cdot \adv^{\dualPRF}_{\HKDF}(\advB_2).
\end{equation}
Neither bound includes an additional session-guessing factor.
\end{theorem}

\begin{proof}[Proof sketch]
The key subtlety is that the first post-compromise directed step uses the
peer's epoch-$e$ DH and KEM public keys. If the corresponding peer DH private
scalar was also revealed, the adversary can compute that first DH contribution
from the sender's new public key. The theorem therefore separates local
state compromise from true two-endpoint state compromise.

\textbf{Part (a):} At the first honest directed step, the honest party generates a fresh DH keypair $(d_{e+1}, D_{e+1})$ unknown to the adversary. If the peer DH private scalar for $D_{\mathit{peer}}$ was not exposed, the DH shared secret is fresh. The KEM encapsulation at that step uses the old $kpk_e^{\mathit{peer}}$ (possibly compromised), so KEM does not contribute security. By $\GapCDH$ hardness and the $\dualPRF$ property, the new root key is pseudorandom in the local-compromise model.

\textbf{Part (b):} During the first honest directed step, the honest party also generated a fresh DH keypair and ML-KEM keypair $(kpk_{e+1}, ksk_{e+1})$ and advertised their public components. At the next directed step that uses these post-compromise public keys, the peer computes DH against the fresh DH public key and encapsulates against $kpk_{e+1}$, whose secret key was generated after compromise. The KEM shared secret is indistinguishable from random by $\INDCCA$, and the DH contribution is fresh under $\GapCDH$. The $\dualPRF$ property gives pseudorandomness of the next root key.
\end{proof}

\begin{lemma}[Per-Direction Ratchet]\label{lem:per-direction}
Aura's per-direction ratcheting (the \path|send_ratchet_pending| flag
set after every received message) ensures every direction change triggers
a fresh hybrid ratchet step. This makes the recovery point explicit in the
implementation: after local state compromise, classical PCS starts at the next
honest ratchet step; after two-endpoint state compromise, recovery is delayed
until a directed step uses post-compromise peer DH and KEM material as described
in \cref{thm:pcs}.
\end{lemma}

\subsection{Theorem 5: Message Confidentiality and Integrity}

\begin{theorem}[Message Security]\label{thm:msg-security}
For fresh partnered sessions under non-adversary-established root keys, and under $\MRAE$ security of $\AEAD$ and $\PRF$ security of the chain KDF, each message key $\mk_{e,n}$ is indistinguishable from random and each ciphertext provides $\INDCPA$ + $\INTCTXT$ security over $q_m$ total encrypted message attempts:
\begin{equation}\label{eq:msg-security-bound}
  \adv^{\mathrm{Conf}}_{\mathrm{AURA}}(\advA) \leq \adv^{\eCK}_{\mathrm{AURA}}(\advB_0) + q_m \cdot \adv^{\PRF}_{\mathrm{chain}}(\advB_1) + q_m \cdot \adv^{\MRAE}_{\AEAD}(\advB_2) + \frac{q_m^2}{2^{96}}.
\end{equation}
\end{theorem}

\begin{proof}[Proof sketch]
The proof first replaces the relevant root key with a random value, using \cref{thm:ake,thm:fs,thm:pcs}. It then applies a hybrid argument over chain indices, replacing each $\mk_{e,n}$ with a random key by $\PRF$ security of the chain KDF. The last step invokes $\MRAE$ security: with random per-message keys, $\AEAD$ provides $\INDCPA$ + $\INTCTXT$. Payload nonces are unique within a chain by construction; the term $q_m^2/2^{96}$ conservatively bounds collisions of random metadata header nonces under the same metadata key.
\end{proof}

\begin{lemma}[GCM-SIV Nonce-Misuse Resistance]\label{lem:gcm-siv}
$\AEAD$ provides full $\INDCPA$ + $\INTCTXT$ under unique nonces, and degrades to deterministic authenticated encryption under nonce reuse: repeated key/nonce/AAD/plaintext tuples expose equality patterns, while $\INTCTXT$ is preserved. This is defense-in-depth: Aura uses monotonic counters that prevent nonce reuse, but GCM-SIV provides graceful degradation against implementation bugs.
\end{lemma}

\subsection{Theorem 6: Replay Resistance}

\begin{theorem}[Replay Resistance]\label{thm:replay}
Assume continuous receiver state and no accepted sealed-state rollback. Exact replay acceptance is zero. For modified replays:
\begin{equation}\label{eq:replay-bound}
  \adv^{\mathrm{Replay}}_{\mathrm{AURA}}(\advA) \leq \adv^{\INTCTXT}_{\AEAD}(\advB).
\end{equation}
\end{theorem}

\begin{proof}[Proof sketch]
Exact replays are caught by the nonce cache while the entry is retained. If the entry has been evicted, the stale message key is no longer derivable from the current chain state, so the same ciphertext still cannot be accepted. Modified replays require forging an AEAD tag and reduce to $\INTCTXT$. Crash recovery is a separate state-continuity assumption enforced by sealed-state counters; without durable state, replay resistance is a system-level contract rather than a pure AEAD property.
\end{proof}

\section{Formal Verification}\label{sec:formal}

The reduction proofs are accompanied by scoped symbolic models in two tools: Tamarin Prover~\cite{meier2013} for trace-based reasoning and ProVerif~\cite{blanchet2016} for Horn-clause analysis. These models are partial evidence for specific abstractions, not a machine proof of the full Rust protocol: the default artifact verifies 10 Tamarin lemmas and discharges 3 ProVerif queries, while the remaining ProVerif checks are documented as disabled, non-terminating, or intentionally negative.

\subsection{Tamarin Prover}\label{sec:tamarin}

\subsubsection{Handshake Model}

The handshake model (\texttt{aura\_handshake.spthy}) uses Tamarin's built-in Diffie--Hellman equational theory and custom function symbols for ML-KEM-768:
\begin{align}
  &\texttt{kyber\_pk}(sk) \to kpk, \label{eq:tamarin-kyber-pk}\\
  &\texttt{kyber\_encaps}(ss, kpk) \to ct, \label{eq:tamarin-kyber-encaps}\\
  &\texttt{kyber\_decaps}(ct, sk) = ss. \label{eq:tamarin-kyber-decaps}
\end{align}

\paragraph{Key design decisions.}
\begin{itemize}
  \item Only 2 of the 4 X3DH DH operations ($\mathit{dh}_1$ and $\mathit{dh}_2$) are modeled to avoid Tamarin's source saturation with $\geq 4$ DH operations. This removes two DH contributions; it is conservative for session-key secrecy, but it does not model every transcript-binding path in the implementation.

  \item A single \texttt{!Keys} fact merges all of a party's key material (identity key, signed pre-key, KEM secret key), preventing cross-instance key mismatch attacks that arise from separate persistent facts.
  \item The symbolic authentication model treats the responder KEM public key as a trusted bundle field, which is stronger than the implementation's shape-validation plus transcript/key-confirmation binding; KEM-key substitution is covered by \cref{lem:augmented-hkdf} and tamper tests.
\end{itemize}

\paragraph{Threat model.}
The Dolev--Yao adversary has full network control. Two compromise rules model different adversary capabilities:
\begin{itemize}
  \item \textbf{Classical compromise:} Reveals X25519 identity and signed pre-key private keys (models side-channel or CRQC).
  \item \textbf{Full compromise:} Additionally reveals the ML-KEM secret key (total break).
\end{itemize}

Classical-only compromise after the session does not break secrecy in that model.

\subsubsection{Ratchet Model}

The ratchet model (\texttt{aura\_ratchet.spthy}) abstracts DH as a classical KEM (avoiding Tamarin's non-termination with DH in state-loop rules) and uses a terminal (single-step) model. It verifies the decomposed PCS/key-agreement shape for that step; the unbounded ratchet PCS statement remains a reduction claim, and augmented KEM-public-key binding is handled by the HKDF lemma and implementation tests.

\paragraph{Key design decisions.}
\begin{itemize}
  \item Ratchet chains (consume+produce state loops) combined with the DH equational theory cause non-termination in Tamarin. We model a single ratchet step with compromise at setup time.
  \item Three setup variants (honest, sender-compromised, receiver-compromised) replace runtime compromise rules, giving the adversary different levels of initial knowledge.
  \item A linear \texttt{SentCt} fact binds sender and receiver within the same session, ensuring the receiver only processes ciphertexts that were actually sent.
\end{itemize}

\subsection{ProVerif}\label{sec:proverif}

The active ProVerif process in \texttt{aura.pv} covers the handshake plus one symbolic message path. It models all four X3DH DH operations, Ed25519 signature verification, and the initial chain KDF over one public Dolev--Yao channel with 10 distinct symbolic types and unbounded session replication. Ratchet functions and augmented-info sketches are present in the file, but they are not invoked by the active process; ratchet PCS is analyzed by the Tamarin ratchet model and the PCS theorem.

\paragraph{Trust model.}
Identity keys are registered in a ProVerif \texttt{table}, modeling out-of-band key verification (TOFU / safety numbers).

\paragraph{Phase-based forward secrecy.}
Phase 0 represents honest execution; phase 1 reveals all long-term keys. Queries Q1 and Q4 are no-compromise phase-0 secrecy checks; Q6 is a stress query for whether the phase-0 KEM shared secret remains hidden after phase-1 disclosure.

Authentication, partnered message integrity, and PCS are supported by the Tamarin models, reduction proofs, and implementation tests.

\subsection{Complementarity of Tools}

The two tools are complementary: Tamarin provides precise DH reasoning but requires abstractions to avoid non-termination; ProVerif handles unbounded handshake/message sessions with all four DH operations and exposes scope errors in overly broad queries. The reported result is therefore 10/10 Tamarin lemmas and 3/6 discharged ProVerif queries, with Q3/Q5/Q6 kept outside the machine-checked claim and ratchet PCS carried by the Tamarin ratchet model plus the PCS proof.

\subsection{Secure Memory Management}

Key material is protected at multiple levels:

\begin{enumerate}
  \item \textbf{Guarded memory allocation.} Long-lived secret keys (DH private keys, ML-KEM secret keys) are stored in \texttt{SecureMemoryHandle} objects. On Linux/Unix targets that permit page locking, this uses \texttt{mlock} and, on Linux, \texttt{MADV\_DONTDUMP}; on platforms that cannot lock pages, the implementation falls back to heap storage with automatic zeroing via \texttt{zeroize} on drop.

  \item \textbf{Zeroize-on-drop.} Intermediate key material (PRK from HKDF extract, chain key copies) is wrapped in \texttt{Zeroizing<Vec<u8>>} from the \texttt{zeroize} crate, ensuring automatic zeroing even on error paths (when the Rust \texttt{?} operator triggers early returns).

  \item \textbf{Explicit wiping.} All DH shared secrets, IKM buffers, classical shared secrets, and ML-KEM shared secrets are explicitly wiped via \texttt{zeroize::Zeroize} (volatile writes with compiler barriers) immediately after use.

  \item \textbf{Timestamp rounding.} Nanosecond fields in message timestamps are deliberately zeroed to prevent device fingerprinting via timing analysis.
\end{enumerate}

\subsection{ML-KEM-768 Integration}\label{sec:kyber-impl}

The ML-KEM-768 integration has three implementation points that affect the protocol artifact:

\begin{itemize}
  \item \textbf{Self-testing.} Random ML-KEM key generation is followed by an immediate encapsulate/decapsulate round-trip with constant-time shared secret comparison. Deterministic seeded generation is reserved for reproducible vectors. The self-test detects KEM correctness failures, including gross RNG or library faults that cause encapsulation and decapsulation to disagree.

  \item \textbf{Deterministic keygen.} For deterministic identity derivation from a master key, the wrapper derives a 32-byte seed and instantiates a local \texttt{ChaCha20Rng}; \texttt{MlKem768::generate} is then called with that local RNG. No global RNG hook or C library state is involved.

  \item \textbf{Bandwidth overhead.} Each hybrid ratchet step adds $1{,}184 + 1{,}088 + 32 = 2{,}304$ bytes to the message envelope (ML-KEM public key + ciphertext + DH public key). For messaging applications with typical message sizes of 100--1{,}000 bytes, this represents a 3--23$\times$ overhead per ratchet step.
\end{itemize}

% 10. OPERATIONAL INVARIANTS
% ═════════════════════════════════════════════════════════════
\section{Operational Invariants Behind the Proof Boundary}\label{sec:operational-invariants}

The formal statements in \cref{sec:proofs} are about an abstract
two-party session protocol. The implementation evidence in
\cref{sec:implementation,sec:evaluation} has a different role: it checks
that concrete parsing, persistence, and error paths do not create traces
that the model deliberately omits. This section makes that boundary
explicit. The goal is not to turn tests into proofs, but to state the
operational assumptions under which the proof model remains a faithful
description of the code path exercised by a message.

\paragraph{Reject without state movement.}
For syntactically invalid input, the required implementation semantics is
a pure rejection:
\begin{equation}\label{eq:reject-no-state}
  \mathsf{Handle}(S, C) = (\bot, S)
  \qquad\text{for every ciphertext or frame } C \notin \mathcal{L}_{\mathrm{Aura}} .
\end{equation}
Here $\mathcal{L}_{\mathrm{Aura}}$ is the set of well-formed protocol
frames with valid version tags, fixed-length X25519 and ML-KEM fields,
bounded counters, and a syntactically present ratchet header whenever the
message type requires one. The implementation checks those conditions
before any secret state is advanced. In particular, malformed protobuf
fields, unsupported versions, incorrect public-key lengths, oversized
payloads, missing ratchet material, and failed AEAD authentication must
not increment message counters, change replay windows, cache partial
keys, or rotate the root key. This invariant is what allows the formal
model to treat malformed traffic as absence of an accepted event rather
than as a third kind of state transition.

\paragraph{Atomic acceptance.}
For valid traffic, acceptance is modeled as a single transition from
state $S_i$ to state $S_{i+1}$. The implementation has to preserve the
same abstraction even though it performs parsing, decryption, replay
checks, chain-key updates, metadata-key updates, and sealed-state export
as separate instructions. The required order is:
\begin{equation}\label{eq:accept-atomic}
  \mathsf{Verify}(C,S_i)=1
  \;\Longrightarrow\;
  \mathsf{Persist}(S_{i+1}) \prec \mathsf{Release}(M),
\end{equation}
unless the caller provides an equivalent durable transaction boundary.
If plaintext were released before replay state and chain state became
durable, a process crash could allow the same ciphertext to be accepted
again after restart. That would not contradict AEAD security or HKDF
pseudorandomness; it would violate the state premise of the replay
theorem. This is why sealed state, the external monotonic counter, and
idempotent restore handling are part of the protocol evidence rather than
mere storage convenience.

\paragraph{Out-of-order delivery.}
Asynchronous messaging cannot rely on FIFO transport. A delayed message
may arrive after a peer has already sent a new ratchet header, and an old
ciphertext may be replayed after a sealed-state import. The implementation
therefore binds skipped message keys and cached metadata keys to the
epoch in which they were derived. Accepting an old but still admissible
message must not roll the root key backward, reinterpret a metadata key
under a later epoch, or make a previously rejected ciphertext valid in a
new state. Bounded caches are part of the same invariant: they prevent an
attacker from forcing unbounded retention of old chain material and make
the replay window a concrete system parameter rather than an implicit
infinite buffer.

\paragraph{Key-directory and downgrade behavior.}
The pre-key directory is not trusted to define the peer's identity. It can
delay updates, replay an old signed pre-key, omit a KEM public key, or
serve different bundles to different clients. Aura's claim is therefore
conditional on identity verification and on a policy decision that the
peer is expected to support the hybrid profile. Under that policy,
absence or substitution of KEM material is a visible protocol failure, not
a silent fallback to a weaker transcript. This distinction matters for
the harvest-now-decrypt-later claim: the hybrid theorem applies to
sessions whose transcript actually contains the ML-KEM contribution
specified in \cref{sec:handshake}.

\paragraph{Why the tests are scoped.}
The 556 scenarios in \cref{tab:tests} are counted because they exercise
the invariants above: domain separation, ratchet atomicity, replay-window
persistence, sealed-state freshness, malformed-input rejection, and
negative session behavior. Tests outside this boundary may still be useful
engineering checks, but they do not enlarge the theorem statement. This
keeps the paper's empirical evidence aligned with the exact two-party
protocol analyzed in \cref{sec:security-model}; broader product surfaces
need their own state models before the same style of claim can be made.

\subsection{Ratcheting Strategy}

In the classical Double Ratchet, the DH ratchet advances when a new DH public key is received from the peer~\cite{signal-double-ratchet}; Signal's current Triple Ratchet adds \SPQR{} as a separate sparse post-quantum component~\cite{signal-spqr,mlkem-braid}. Aura uses per-direction hybrid ratcheting for this design point: after every received message, the \texttt{send\_ratchet\_pending} flag causes the next send to trigger a full hybrid ratchet. This provides:

\begin{enumerate}
  \item \textbf{Per-direction forward secrecy.} Each direction change creates a new root key, limiting the damage of a chain-key compromise to the affected direction and epoch.
  \item \textbf{Explicit PCS recovery point.} After local compromise, classical PCS starts at the next honest ratchet step. After two-endpoint state compromise, recovery needs a directed step that uses peer DH and KEM material generated after the compromise.
  \item \textbf{Per-ratchet PQ contribution.} Every ratchet step includes fresh ML-KEM-768 key material, so post-quantum material is refreshed beyond the initial handshake.
\end{enumerate}

\paragraph{Cost.}
Each hybrid ratchet step adds $\sim$259\,$\mu$s of computation and 2{,}304 bytes of bandwidth overhead (1{,}184 bytes for the ML-KEM public key, 1{,}088 bytes for the ML-KEM ciphertext, 32 bytes for the DH public key). For interactive messaging with alternating messages, the measured profile is $\sim$280\,$\mu$s/msg; the $\sim$15\,$\mu$s/msg burst number is a decrypt-only measurement over pre-generated same-direction envelopes.

\subsection{PCS Recovery: 1-Step vs.\ 2-Step}

Signal-style DH ratchets achieve PCS once an uncompromised DH contribution
enters the root chain. Aura separates two cases. If only the local endpoint
state is compromised, the next honest directed step gives 1-step
\emph{classical} PCS via $\GapCDH$ on fresh DH material. If both endpoints'
epoch state is compromised, the first directed step may still use peer
ratchet state exposed before recovery; hybrid recovery is claimed only once a
directed step uses peer DH and KEM material generated after the compromise.
\Cref{thm:pcs} formalizes that recovery boundary for the construction analyzed
in this paper.

\subsection{Identity Binding}

Signal-style protocols obtain identity binding through authenticated key-agreement transcripts, signed pre-keys, and associated data. Aura adds an explicit implementation-level identity binding hash $\mathit{ibh} = \SHA(\texttt{"Aura-Identity-Binding"} \concat \mathrm{sort}(\cdot))$ embedded in every AEAD additional data field. Benefits include:

\begin{itemize}
  \item Explicit identity inclusion prevents cross-session identity confusion.
  \item Lexicographic sorting gives a stable unordered peer-set binding; role
        separation comes from transcript/key-confirmation domains and
        send/receive chain assignment.
  \item Domain separation prevents cross-protocol key reuse.
  \item The hash appears in both metadata and payload AAD, providing protection at both layers.
\end{itemize}

\section{Discussion}\label{sec:discussion}

\subsection{Bandwidth Overhead}

The primary cost of per-ratchet hybrid key exchange is bandwidth: each ratchet step adds 2{,}304 bytes to the message envelope. For short text messages ($\sim$100 bytes), this represents a $23\times$ overhead per ratchet. Several mitigations are possible:

\begin{itemize}
  \item \textbf{Batching:} In burst messaging scenarios (multiple messages in the same direction), only the first message carries the ratchet header; subsequent messages in the same epoch have zero KEM overhead.
  \item \textbf{Compression:} No compression is assumed in the protocol. Any compression of KEM-related fields should be treated as future work and analyzed for security and side-channel effects.
  \item \textbf{Smaller KEM:} ML-KEM-512 (NIST Level 1) reduces the per-ratchet overhead to $1{,}568$ bytes ($800 + 768$) at the cost of lower quantum security ($\sim$118 bits).
\end{itemize}

\subsection{2-Step Hybrid PCS}

The 2-step hybrid PCS recovery follows from the directed KEM-public-key ratchet used in Aura. After a local compromise, the first honest directed step can restore classical security through a fresh DH contribution. After full two-endpoint state compromise, however, the peer DH and KEM state used by that first directed step may already be exposed, so no one-step recovery is claimed. Full hybrid recovery is restored on a later directed step that uses peer DH and KEM material generated after the compromise.

Within this KEM-public-key ratchet pattern, one-step hybrid recovery would require a different schedule, such as simultaneous KEM-key transport, explicit acknowledgements, or another post-quantum SCKA design. We leave that design space outside this paper rather than claiming a lower bound.

\subsection{ProVerif Limitations}

Three of six ProVerif queries are not discharged by the current model. Q3 (injective authentication) does not terminate in the default four-DH artifact. Q5 is false for an unpartnered active trace and therefore does not match the partnered-session integrity theorem. Q6 is false because raw KEM shared secrets are recoverable after the corresponding KEM secret key is revealed. These queries are not counted as machine-checked results; the claimed properties are carried by the Tamarin-style authentication/secrecy/PCS models, reduction proofs, and implementation tests.

\subsection{Kyber/ML-KEM Terminology}

The code keeps the historical wrapper name \texttt{KyberInterop}, but the cryptographic implementation uses the Rust \texttt{ml-kem} crate and the \texttt{MlKem768} type. Moving to a certified FIPS ML-KEM module in a production supply chain would affect the provider boundary, not the protocol logic or the proof structure. The hybrid combiner's security relies on $\INDCCA$ security of the KEM, which ML-KEM provides.

\subsection{Operational Profiles}

The intended operating point is asynchronous text messaging. In that setting,
a full hybrid ratchet on direction change keeps the recovery rule simple while
amortizing the 2.3~KB ratchet header over bursts of messages sent in the same
direction. After a local state compromise, the first honest ratchet step restores
the classical DH contribution; after full two-endpoint state compromise, recovery
is tied to a later directed step that uses post-compromise peer DH and KEM
material.

Latency-constrained profiles with a hard per-packet budget are a separate design
point. The handshake can still establish an authenticated hybrid secret, but the
ratchet schedule would need its own timing, acknowledgement, and loss model. The
two-party messaging theorem should not be read as a proof for such a profile
unless that profile carries its own state machine and recovery argument.

Long-lived desktop and server-side sessions put pressure on a different part of
the design: sealed state. A valid encrypted state blob is not necessarily a
fresh state blob. Backup restore, VM snapshots, and storage migration can replay
an old but correctly authenticated state. The sealed-state counter is therefore
part of the protocol integration, not merely a serialization detail. Without an
external monotonic value, AEAD and HMAC authenticate the blob but cannot tell a
current state from an older valid one.

Multi-device accounts introduce another boundary. The current model treats a
session as a two-party channel between two devices. If one user has several
devices, the system has to decide whether to run separate pairwise sessions,
fan out messages through a Sesame-like session manager, or introduce a separate
multi-device state-management layer. These choices affect replay windows, identity binding,
device removal, and sealed-state freshness. They are product-level choices, and
they should not be hidden inside the two-party theorem statement.

\subsection{Reproducibility Boundary}

The paper separates three levels of evidence. The first level is the protocol
argument: theorems state which assumptions are used and where the losses enter.
The second level is symbolic verification: the Tamarin and ProVerif models
check trace properties under their respective abstractions. The third level is
the Rust implementation: tests check serialization, nonce behavior, replay
state, skipped-key handling, and recovery after malformed envelopes.

This separation is deliberate. A proof about an idealized state transition does
not automatically prove the byte parser, and a passing test suite does not
replace the reduction. The implementation cross-reference map is useful because it records where
an invariant is supposed to live: in a theorem, in a model lemma, in a module
boundary, or in a regression test. When the code changes, the map gives a small
checklist of claims that must be re-evaluated.

The comparison with deployed systems should be read in the same way. Signal
\SPQR{} and Apple \PQThree{} provide the relevant deployment references; Aura
does not make a claim about user scale or operational maturity. Its
contribution is an inspectable artifact in which ratchet state, KEM-key
binding, metadata-key rotation, sealed-state rollback handling, and test
coverage are visible in one implementation.

The artifact includes a reproducibility script with
quick, test, formal, paper, bench, and full modes. A dedicated paper-vector test
and a matching dump utility fix deterministic vectors for HKDF, AES-GCM-SIV,
seeded ML-KEM public-key generation, master-key identity derivation, the full
handshake transcript, the first post-handshake envelope, the first
DH+KEM-ratchet envelope, and multi-epoch delayed-delivery envelopes under a
test-only deterministic entropy feature. Each artifact run emits tool versions,
a manifest, and SHA-256 checksums; release CI uploads the quick and paper-build
logs as a reviewable artifact bundle, and the formal CI job uploads
Tamarin/ProVerif stdout/stderr logs with the same manifest and checksum format.
Release-tag benchmark workflows produce retention-limited artifacts for the
fixed traffic-profile comparisons. The remaining evidence gap is independent
review: the implementation cross-reference map is author-maintained until an external reviewer
records model/code alignment using the review package.

\subsection{Limitations}

\begin{itemize}
  \item \textbf{No post-quantum signatures.} Aura uses Ed25519 for identity and SPK signatures. A CRQC could forge signatures to mount impersonation attacks against the initial handshake. Moving to PQ signatures (e.g., ML-DSA/Dilithium) would require larger signatures and a deployment migration, but it is orthogonal to the ratchet argument studied here.
  \item \textbf{Trust-on-first-use.} The protocol assumes out-of-band verification of identity keys (safety numbers). Compromised key distribution is outside the threat model.
  \item \textbf{Single-device.} The current session model assumes a single device per user. Multi-device support would require session fan-out or Sesame-like session management.
  \item \textbf{Two-party proof scope.} The reduction-style theorems and symbolic models cover the analyzed two-party session protocol. Other implementation modules require separate state models before the same claims can be made for them.
  \item \textbf{Ratchet cost.} Per-direction KEM rotation adds a 2.3~KB ratchet header and about $259\,\mu$s of ratchet work in the measured profile. Any lower-frequency ratchet profile would need its own PCS and cost statement.
  \item \textbf{Sealed-state freshness.} AEAD and state HMACs protect serialized state integrity, but rollback protection needs an external monotonic counter or equivalent freshness anchor.
\end{itemize}

\section{Conclusion}\label{sec:conclusion}

Aura isolates a concrete design point for hybrid post-quantum confidentiality in secure messaging: KEM material is refreshed in continuing ratchet state, while identity authentication remains classical in the current artifact. The protocol combines per-ratchet KEM-key rotation, explicit KEM-key binding, per-epoch metadata encryption, and nonce-misuse-resistant AEAD.

The evidence is split into layers a reviewer can check: 6 reduction-style theorems, 10 Tamarin lemmas over decomposed abstractions, 3 discharged ProVerif queries, an implementation cross-reference map, and a Rust implementation. The current implementation measures approximately $1.1$\,ms for the full handshake, $280\,\mu$s/msg for alternating 256-byte messages, and $15\,\mu$s/msg for pre-generated same-direction decrypts. These are cost snapshots, not security claims; the paper-scope test subset is reported separately from implementation modules outside the analyzed theorem boundary.

\bottomrule
\end{tabular}
\end{table}

Delayed old-epoch metadata decryptability is bounded by both
\texttt{MAX\_CACHED\_METADATA\_KEYS} and
\texttt{MAX\_METADATA\_KEY\_EPOCH\_AGE}; the implementation evicts by count and
by epoch age.

\section{Wire Format}\label{app:wire-format}

All messages are serialized using Protocol Buffers v3 (\texttt{prost} crate). The primary wire-format messages are:

\paragraph{Pre-Key Bundle.}
\begin{lstlisting}
message PreKeyBundle {
  uint32 version = 1;
  bytes  identity_ed25519_public = 2;
  bytes  identity_x25519_public = 3;
  uint32 signed_pre_key_id = 4;
  bytes  signed_pre_key_public = 5;
  bytes  signed_pre_key_signature = 6;
  repeated OneTimePreKey one_time_pre_keys = 7;
  bytes  kyber_public = 8;
  bytes  identity_x25519_signature = 9;
}
\end{lstlisting}

\paragraph{Handshake Init.}
\begin{lstlisting}
message HandshakeInit {
  uint32 version = 1;
  bytes  initiator_identity_ed25519_public = 2; // 32 bytes
  bytes  initiator_identity_x25519_public = 3;  // 32 bytes
  bytes  initiator_ephemeral_x25519_public = 4; // 32 bytes
  optional uint32 one_time_pre_key_id = 5;
  bytes  kyber_ciphertext = 6;        // 1088 bytes
  bytes  key_confirmation_mac = 7;    // 32 bytes
  bytes  initiator_kyber_public = 8;  // 1184 bytes
  uint32 max_messages_per_chain = 9;
  bytes  initiator_identity_binding_signature = 10; // 64 bytes
}
\end{lstlisting}

\paragraph{Secure Envelope.}
\begin{lstlisting}
message SecureEnvelope {
  uint32 version = 1;
  bytes  encrypted_metadata = 2; // AEAD(mdk, metadata)
  bytes  encrypted_payload = 3;  // AEAD(mk, plaintext)
  bytes  header_nonce = 4;       // 12 bytes
  uint64 ratchet_epoch = 5;
  // Present only on ratchet steps:
  bytes  dh_public_key = 6;      // 32 bytes
  bytes  kyber_ciphertext = 7;   // 1088 bytes
  Timestamp sent_at = 8;         // nanoseconds zeroed
  bytes  new_kyber_public = 9;   // 1184 bytes
  uint64 previous_chain_length = 10;
}
\end{lstlisting}
